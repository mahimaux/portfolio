small: Figure 1. One task, four handoffs. Each break leaves the person with a question the chat can't answer.
card: 1 · Plan // Unclear scope :: The plan lives inside the model. Steps scroll past in the conversation. :: _What will it do next, and with which tools?_
card: 2 · Send // Vague consent :: "Send the email?" is a plain yes or no. One yes feels like permission for every email. :: _Which email, to whom, saying what? Can I take it back?_
card: 3 · Edit // Stale approval :: The agent edits the draft after I approve it. My old yes quietly carries forward. :: _Does my approval still cover this version?_
card: 4 · Fail // Lost work :: The run stops at step three. Nothing shows which finished work survived. :: _What survived, and do I have to start over?_
label: Problem statement
p: **People who hand multi-step work to AI agents need to know three things at every handoff:**
list: What will happen next
list: Exactly what they are approving
list: What survives a failure

# 05 / Key design decisions || Four decisions shaped what ATLAS is.
p: Each one uses the same format: problem, options, choice, trade-off, screen.
label: 01 · Supervision is a workspace, not a chat · Principle: show the next action
rows: Problem | Supervising means coming back and checking at a glance. In a chat, "where is my task?" means scrolling.
rows: Options | Chat thread (ruled out) · **Supervision workspace** (chosen)
rows: Choice | Nine named task states, not just "running" and "done". Every card, stage and event names the agent that owns it.
rows: Trade-off | Nine screens are more to learn than one text box, and it's weaker for quick, open-ended requests. The workflow graph was unreadable at 375 px, so I added a list view.
figs: s-workflows | Workflows: each stage shows the agent that owns it and its state.
label: 02 · Consent is tied to one exact revision · Principle: one exact scope
rows: Problem | "Approve this email?" asks people to vouch for something they haven't seen. Worse, an old yes carries over to a new edit.
rows: Options | Approve a summary (ruled out) · **Approve one exact revision** (chosen)
rows: Choice | Consequence Preview: all 8 recipients, exact subject and body, shared data, and whether it can be undone. Approve stays disabled until the person confirms they reviewed this revision. Any edit creates a new revision and clears the approval.
rows: Trade-off | It's dense, especially at 375 px, and every edit means another review.
figs: s-consequence | Consequence Preview: the reach of the action, before the decision.
label: 03 · Permission is separate from approval · Principle: two separate checks
rows: Problem | People read a toggle labelled "can send email" as "yes to all emails". Better copy can't fix that. The structure has to change.
rows: Options | One "can send" toggle (ruled out) · **Permission + exact approval** (chosen)
rows: Choice | Six permissions scoped to one task, checked before every step. Sending needs the permission and an exact approval. Revoking mid-run blocks future steps and keeps finished ones.
rows: Trade-off | Two ideas to understand instead of one, so the screen carries explanatory copy: "A boundary, not a blank cheque."
figs: s-permissions | Permissions: six task-scoped switches, with the rule spelled out.
label: 04 · Failure keeps the work and retries from the break · Principle: keep the work
rows: Problem | If a run that dies at stage 3 costs you stages 1 and 2, delegation stops being worth it.
rows: Options | All-or-nothing restart (ruled out) · **Keep work, retry from the break** (chosen)
rows: Choice | Outputs saved per stage. Recovery Center shows what survived. "Inspect saved work" comes before "Resume". Retry starts at the failed stage, with no duplicate outputs.
rows: Trade-off | More states and retry rules to explain. Saved work lives only in the browser. A production version would need durable server-side jobs.
figs: s-recovery | Preserved work: the banner says what's safe before it says what broke.

# 07 / How I worked with AI || Codex wrote the code. I directed it, reviewed it and decided when it was done.
diagram: d-ai | The loop for each milestone: I write the scope and acceptance criteria, Codex restates it, I say yes, Codex builds, automatic gates run, and I review it in the running app before it counts as done
small: Figure 5. Nothing new was built without my yes, and nothing counted as done until I'd reviewed it in the running app.
card: What I directed :: Scope for every milestone, restated back to me before building :: Acceptance criteria a test can check: "No approval survives an edit" :: All product, IA, interaction and UX writing decisions
card: What the gates I set caught :: Status showed the coordinator, not the agent doing the work :: A stale tab lost a task made in another tab :: The guided demo ticked steps after a rejected plan :: Copy called a real-looking address "fictional"
card: Where I said no :: A cloud code review that would have sent the source code off my machine :: A forced major downgrade to clear a lint-tooling warning. I documented it instead.

label: Reflection
p: **The worst bug was the problem I was designing against.** Status showed the wrong agent, which is exactly the "who did this?" confusion ATLAS exists to prevent. Visible responsibility needs a test, not just intent.
p: **Honesty became a design constraint.** "Say what is simulated" shaped real UI: the Demo Mode chip, labelled sample charts, and milestones that tick only when work happened.
p: **My riskiest decision is the one I most want tested.** Consequence Preview shows everything, and that may be too much.
